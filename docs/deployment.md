# 部署、旧库迁移与恢复

## 上线前准备

复制 `.env.production.example` 为本机/服务器的 `.env.production`，填写实际数据库账号、64 字节以上独立随机 JWT_SECRET、管理员初始口令、微信 AppID/Secret 和 OSS 信息。真实值不要提交 Git。

生产默认禁止微信 mock；缺少微信配置、密钥或 OSS 配置会拒绝启动。图片经过格式校验和重编码，图片对象可公开；视频对象为私有，鉴权后签名。使用默认私有 bucket，并在真实 OSS 验证匿名拒访、签名过期、权限变化和图片显示，不能用本地模拟器代替这些验证。

后台应用只支持单门店。代码保留历史门店字段以兼容原库，但新用户、资金操作和前台课程按门店 1 处理；不要加载其它演示门店种子数据。

## 旧库接入 Flyway

1. 停止旧后端写入及其定时任务，记录应用版本和数据库快照。
2. 用 `mysqldump --single-transaction --routines --triggers` 做加密保存的备份；密码使用交互输入或受保护的 MySQL defaults 文件，不拼在公开命令里。
3. 在备份恢复的副本上执行新版迁移。已有全部旧表的库首次接入时设置 `DB_BASELINE_EXISTING=true`，Flyway 以版本 1 为基线，执行 V2 及以后的迁移。空库不要启用 baseline。
4. V2 会核对 `用户可用+冻结=批次剩余合计`、`冻结=有效预约冻结合计`，并检查重复有效预约。不一致时报告用户/课次 ID 并停止。不要直接改余额掩盖问题；结合原充值、预约、签到流水处理原始数据后再重试。
5. MySQL DDL 不支持完整事务回滚。若迁移在 DDL 后失败，应检查 Flyway 历史与错误，再由操作者执行 repair、重新运行；迁移的字段与表创建设计为可重试，数据迁移有事务保护。不要删除 migration 历史表或重复执行旧 schema.sql。
6. 副本验收成功后，对已备份的正式库升级；成功后把 `DB_BASELINE_EXISTING` 改回 false。启动新后端并验证余额、预约数、签到与领取记录。

旧 `back-end/sql/` 中的建表/造数脚本保留用于理解历史，不作为生产发布命令。新版生产使用 `src/main/resources/db/migration` 和 `src/main/java/db/migration`。不运行旧脚本中的 DROP TABLE、批量删除和示例插入。

V5 取消冻结课时：已有正式预约转换为已扣课记录，可用余额不重复扣除，批次剩余同步减少；历史候补占用的有效课时在升级时退回并记流水，已过期部分不恢复。随后删除 `user.frozen_hours`、`course_hour_batch.frozen` 和 `booking.locked_hours`。预约到原批次的记录保留，供取消退款核对。运行时统一按“预约扣课、签到不再扣、正常取消退回有效课时”处理。

V1/V2 保留旧字段引用以保证已有库的 Flyway 校验与升级；当前代码不再使用这些字段。V5 先校验并事务转换账目，再删除字段，转换后遇到 DDL 失败可按上述 repair 流程重试。升级期间停止旧后端写入，新旧后端不能同时连接升级后的库。

## 发布

生产数据库预先创建，运行账号只赋予目标库所需权限；迁移阶段可使用专用有 DDL 权限账号，常规运行使用只读写业务表的账号，并设置 `SPRING_FLYWAY_ENABLED=false` 避免运行账号执行迁移。运行时仍需读取 schema 已处于正确版本。

```sh
docker compose build
docker compose up -d
docker compose logs --tail=100 api
```

管理后台只向本机 `127.0.0.1:8088` 开放，由服务器 HTTPS 网关转发。配置域名证书、自动续期和微信合法域名；API 与后台同域时不需要开放 CORS。不要用 Vite dev server 承载生产访问。

`front-end/nginx.conf` 已配置页面刷新回退、API 转发、登录限流和基础响应头。HTTPS 网关是外部部署条件，本次没有创建或发布真实域名证书。

微信小程序发布使用 `npm run build:release` 并提供 `VITE_API_BASE_URL`。正式包上传完成后，以真实微信扫一扫验收新用户、旧用户、重复扫码、已取消课次及过期签到码。

## 运行检查与告警

- 外部监控定时 GET `/api/public/studio`，检查 HTTP 成功和业务 code=0；该接口依赖数据库可用于基本可用性检查。
- 监控后端退出/重启、5xx、业务错误异常增长、磁盘空间、数据库容量、慢查询和备份失败；将告警接入门店实际使用的通知渠道。
- 服务与 MySQL 时区统一为 Asia/Shanghai；容器设置 TZ，数据库连接显式配置 serverTimezone。
- 定时任务处理结束课次、未转正候补、爽约和未预约课时过期。单门店事务锁在数据库中生效，多实例也不会各自重复记账；上线仍建议先运行一个后端实例。
- 配置变更写 `configuration_change`；充值、积分、课时变更保留流水；发放记录含核销人、领取时间和领取码。日志不输出密码或 token。

## 备份与回退

每天自动备份并保留独立副本；定期从备份恢复到隔离数据库，核对用户数、余额、预约和兑换记录。具体备份保留周期、加密存放位置和告警接收人需由部署负责人配置。

发布失败首先停止写入，保留失败现场。新旧应用的账目模型不同，不能只换回旧 JAR 而继续使用新结构中的新增交易。回退应恢复同一时间点的应用和数据库备份；若新版本已产生业务交易，应先导出并核对这些增量记录，由操作者决定恢复/补录方案。
